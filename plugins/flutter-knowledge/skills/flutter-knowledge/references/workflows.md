# Task workflows

This reference owns task routing, handoffs and the final completion report. The skill map owns conventions and each specialist owns its detailed instructions. Read the applicable route once per task; direct specialist invocation uses the same route without recursively restarting the map. Load only specialists needed by the requested changes.

## Establish scope and configuration

Identify the requested outcome: explanation, planning, implementation, initialization, tests or review. Preserve explicit source paths, screen/feature scope and project constraints. Do not turn planning into implementation or a local fix into whole-app redesign.

Read existing configuration once when package mechanics matter, then inspect relevant installed APIs and project contracts. Reuse those decisions across skill handoffs; reread only when configuration/dependencies change or a new category becomes relevant. Follow the [configuration contract](../../flutter-init/references/configuration.md). During authorized implementation, invoke `flutter-init` if configuration is absent. Planning, explanation and findings-only review never create or refresh it implicitly. Missing config in those modes is an assumption or finding, not permission to write it.

An unresolved package blocks only changes dependent on that choice. Continue independent work and record the unresolved category. For review, the helper may stop early on configuration issues; use `flutter-review`'s independent read-only fallback and report the incomplete checks. Never pick a competing backend by majority usage or disable a convention. Configuration defaults are selections, not instructions to install packages.

## Core readiness during implementation

After resolving the implementation scope and required inputs, inspect relevant shared APIs and their callers. Search existing equivalents through config discovery and live source, including locations outside `lib/core`. A missing folder, conventional filename or inspector row alone does not establish a missing foundation. Dependency declarations do not establish a working core either.

- **Fresh app without a foundation:** when asked to implement an app, screen, feature or app-wide foundations in a confirmed empty/unchanged Flutter starter with no implemented features or equivalent core, invoke `flutter-core` automatically for the full shared foundation, then return to the requested work. Judge starter source independently of package count: explicit `flutter-init` may already have populated dependencies. A project with existing feature code is not a fresh starter merely because its core folder is absent.
- **Existing or partial core:** invoke `flutter-core` only for a proven missing/incomplete shared contract required by this task, plus the dependencies and wiring necessary to make that contract work. Record that scoped completion in working context before handing off. Ignore unrelated missing inventory rows. An absent optional wrapper is not a core blocker when the UI skill permits a working raw fallback; normal token additions, routes and feature registrations remain with their owning skills. A legacy theme lacking AppTokens follows the existing older-theme exception, not automatic migration.
- **Ready equivalents:** reuse them and proceed without invoking `flutter-core`. Preserve working constructors, routes, providers, theme values, cache keys, assets and existing package choices. Do not create a competing conventional implementation merely to match a path.
- **Explicit `/flutter-core` or a request to prepare the entire core:** inspect and complete the full shared foundation, preserving working equivalents. A user who explicitly limits core completion to named responsibilities retains that scope.

This gate applies only to authorized implementation. Explanation, planning, initialization-only, findings-only review, comparison-only runs and test-only requests inspect/report gaps without bootstrapping core. Missing/ambiguous design inputs do not independently authorize setup; resolve the source and scope first and continue read-only work that does not depend on them. Respect explicit instructions to leave core unchanged: use an allowed existing fallback or report the concrete blocker.

Briefly state the detected gap and chosen scope, then continue without asking the user to name skills or approve routine dependency completion. Ask only for an unresolved package/product decision or missing input. Automatic configuration initialization stays config-only; core completion adds only packages actually needed by its selected responsibilities. Do not install the entire catalog, invent auth/backend policy, migrate unrelated code or reset working styles.

Pass `flutter-core` the origin (fresh bootstrap, scoped dependency completion or explicit request), selected responsibilities and the task to resume. It owns core edits and their validation; the calling workflow resumes against the actual resulting APIs without restarting setup. Reuse an active core scope instead of recursively invoking it through a mini-skill. A later request reevaluates only its dependencies; completed core is not bootstrapped again. Final review may send in-scope fixes back to implementation, but review itself never writes. Report unrelated gaps separately without calling the whole core complete or blocking independent finished work.

## Natural-language design updates

Treat "the login UI changed; update it from the design" as an existing-screen implementation request even when the user names no skill. Select HTML or Figma inspection from the source, then load only the conventions touched, visual verification and the final review. Explain the intended scope in plain language and proceed; do not ask the user to invoke these skills or approve a routine handoff. Questions and review-only requests retain their own routes; review-only consumes existing evidence and reports missing/stale comparisons without starting captures, fixes or baseline updates.

Resolve the source from an explicit attachment/path/frame first, otherwise from an unambiguous source already associated with this screen in the conversation or existing design reports/briefs. Inspect that source and the route/screen files to confirm the association. Reuse a previously supplied path when it still resolves, but never silently substitute an unrelated HTML file, choose the newest of several exports or infer a Figma revision from its URL. If the source or target remains ambiguous/unavailable, ask one concise question for the missing design or screen identity; continue independent inspection. A filename alone is not proof of which screen it contains. An updated version of the app's own design with no named screen is not ambiguous: infer the target as described below.

When the user only says the design changed, infer scope from the source instead of asking. Compare the updated source with what the app currently implements (cached source facts/references, or current theme values and captures of implemented screens) and list each changed rule. A change to root/theme variables or a shared class is app-wide: route it to the owning token/default and treat every consumer screen as affected. A rule whose selector is limited to one screen, mode or state applies only there. Apply every detected change, state the inferred scope in the report, and ask only about a change that cannot be attributed. Report mismatches that predate the update instead of fixing them, unless the user asked for a general fidelity pass; screens outside the inferred scope keep their current output.

Read the existing screen, body/widgets and state-owner wiring before edits. Retain working API/repository calls, controller ownership/disposal, validation, submit/loading/error handling, navigation and route/DI ownership. Update the existing implementation rather than scaffolding a parallel screen. New visual arrangements must still expose its existing actions and operation states. If the design changes an interaction or removes a working action, retain its behavior where compatible; ask about an unresolved product decision rather than inventing new business rules. Do not migrate unrelated legacy code as part of a UI refresh.

Inspect the selected screen's current source states and visible composition, shared styles/assets it depends on, and current theme/wrapper APIs. Refresh invalidated source facts and references through the existing cache contract. A change elsewhere in the whole prototype does not authorize implementing its other screens. For a local update, use existing tokens/assets or source-backed semantic additions and scoped wrapper variants through the owning skills, preserving unrelated defaults. Inspect actual shared consumers before altering an existing token/default.

When the request includes app-wide foundations, select `set-theme-from-html` automatically for a whole HTML source, then the screen reader for the requested screens. If a local screen exposes a shared-foundation mismatch, prefer a scoped variant; when matching requires changing other screens or shared defaults beyond the requested or inferred update, present the concrete impact and ask for that scope decision. Do not run the whole-design theme workflow for every screen update. Apply the [core readiness gate](#core-readiness-during-implementation) only after implementation inputs and scope are resolved; source inspection alone never creates core.

Verify preserved behavior with existing affected checks and the workflow's required state/lifecycle checks, then compare current Flutter output against the updated source at matching profiles. Reuse the capture harness; source comparison and golden regression remain separate. An old Flutter golden cannot establish the new design's fidelity. Inspect and resolve diffs before proposing reviewed new regression baselines; never overwrite baselines just to make an old test pass. When shared code or a token changed, compare each affected consumer screen against the updated source at matching profiles; a Flutter before/after comparison alone does not verify them. Finish with what changed, behavior checks, source/Flutter/diff links, measured differences and remaining gaps. Report missing-source work as not verified rather than inventing a reference or a percentage.

## Efficient execution without weaker checks

Use one agent for ordinary screen/feature work. Additional agents are for explicitly requested reviews, genuinely independent larger tasks or required skill-authoring/benchmark validation. Do not create a second worker merely to reread the same source or rerun the same checks.

Load the map/route and relevant specialists once, retaining decisions through handoffs. Read specific files and extracted facts, not entire repositories, giant escaped HTML payloads or complete passing-test logs. Reuse source inputs through the [validated cache contract](../../visual-verification/references/design-cache.md); changed source/assets/profile/renderer invalidate reuse. Reuse an existing capture harness and add the task's needed cases; do not build another harness or install absent default packages.

Resolve unmatched source values before implementation through the [early design decision](../../flutter-app-theme/SKILL.md#early-design-decision). Exact-source authorization uses the existing source-of-truth rule. Scale-preserving work discloses mappings and the likely fidelity gap; unresolved conflicts get one concrete bundled question while independent work continues. Do not spend visual rounds trying to fix a deliberately different mapping.

Before the full capture matrix, run the [core and capture preflight](../../visual-verification/references/preflight.md), including the compact applicable calibration checks for effective typography, source-layout versus crop scaling, field paint bounds and shared composition. Reuse only matching inspected calibration inputs; calibration does not certify a screen. Keep pre-existing styling mismatches visible without expanding a scoped update into unrelated repairs. Run the applicable pending-operation/disposal and combined Arabic/large-text/narrow/keyboard checks before visual polish. For multi-row design work use the [verification runner](../../visual-verification/references/runner.md), correct with targeted rows and keep one complete final run.

Select state rows through [adaptive coverage and handoff](../../golden-tests/references/coverage-handoff.md): inspect reachable source states and actual owner/control behavior, retain supported main variants and targeted risk combinations, and declare missing/unsupported evidence. Source-backed variants require their own fresh comparison; unprovided variants use behavior/regression evidence without invented references. After actual PNG inspection, finish local baseline promotion and an ordinary non-update golden check. An authorized UI update needs no extra user confirmation for that local handoff; commits/publication remain separate. Do not stop at capture candidates or silently omit a required state.

During fixes, run relevant focused tests/captures. The final flutter-review invocation owns required whole-project analysis/tests once the batch settles; do not duplicate that suite immediately before the gate. Baseline checks and more frequent project requirements remain required. New changes/failures after the gate trigger relevant checks again. No old result or cache hit substitutes for validating changed code.

Keep full command output in local evidence logs; give the agent summaries, exact failed cases and artifact paths. Use comparison JSON for machine-readable evidence, preserving exits/settings, then inspect PNGs. A contact sheet is triage of all required changed variants, not permission to omit any. Open full-resolution images wherever labels, geometry, state, direction or differences are uncertain. Unresolved inspection cannot become VERIFIED. No required variants, behavior/accessibility checks, comparisons or manual review items are removed for efficiency.

During design-driven implementation, record stage work using [stage measurement](../../visual-verification/references/stage-usage.md): source inspection, calibration, implementation, verification, baseline handoff and review. Use available provider counters and measured local timings/counts; missing stage tokens remain unavailable. Whole-task counters are not a guessed breakdown. Compare savings only on the same task/input/coverage/model/renderer, retaining every required state, behavior check and final comparison. Bookkeeping stays internal; never ask the user to supply token counts or choose the specialist sequence.

## Select the route

| Request | Lead and sequence | Completion |
| --- | --- | --- |
| Explain code or discuss architecture | Map → relevant convention references → answer grounded in the project | Explanation; no initialization, app changes or automatic test runs |
| Initialize/refresh selections | `flutter-init` | Config, detected/recommended choices and unresolved categories; explicit empty-starter initialization also prepares selected dependencies; no app/core implementation |
| Plan a whole app from HTML/Figma | Matching source reader → existing foundation inspection → [design briefs](design-briefs.md) | Source inventory, proposed foundations, screen briefs and planned verification coverage; no Dart/theme edits or SDK prerequisite |
| Implement a screen/component from HTML/Figma | Matching source reader (complete visible composition) → core readiness gate → relevant implementation skills → core/capture preflight → earlier behavior checks → `visual-verification` → `flutter-review` | Built scope plus per-screen comparison evidence and final report |
| Update an existing screen after its HTML/Figma design changes, with or without a slash command | [Resolve source and existing behavior](#natural-language-design-updates) → matching source reader → core readiness gate → scoped UI/theme implementation → affected behavior checks → `visual-verification` → `flutter-review` | Updated existing screen with preserved logic, current-source comparison and reviewed regression changes; unrelated screens stay outside implementation scope |
| Implement an entire app or multi-screen feature from a design | Matching source reader → briefs where needed → core readiness gate → implement and verify each screen → final `flutter-review` | Every requested screen accounted for, including blocked/unverified ones; do not stop at briefs |
| Apply or refresh app-wide foundations/assets from a whole HTML design | Resolve source → core readiness gate → `set-theme-from-html` using shared HTML extraction → `flutter-app-theme`/owning UI skills → targeted source-backed foundation/component verification → `flutter-review` | Requested foundation groups/assets applied with role mappings and honest evidence; complete preparation covers all seven groups, while scoped refreshes preserve other groups; later screen work uses `html-to-widget` |
| Implement design foundations | Source reader → core readiness gate → `flutter-app-theme` and relevant shared-widget conventions → verify affected in-scope reference-backed screens → `flutter-review` | Requested tokens/theme/components and their verification; no unrelated screen rewrite |
| Bootstrap or complete shared core (explicit request or automatic readiness handoff) | Selected core scope → config-only `flutter-init` when needed → `flutter-core` inspection and owning convention skills → affected preflight/checks → resume calling task or finish with `flutter-review` | Created/completed/preserved components for the selected scope, selected mechanics, missing decisions and executed checks; partial completion is not a whole-core claim |
| Implement/fix code without a design | Core readiness gate → relevant convention skills → scoped implementation → existing affected tests and analysis → `flutter-review` | Correct requested behavior and honest checks; no invented screenshot reference |
| Write unit tests | `flutter-testing` plus conventions for code under test → run focused tests → `flutter-review` | Requested meaningful coverage and outcomes |
| Add/debug golden regression tests | `golden-tests` → run relevant tests → `flutter-review` | Reviewed baselines/failures; source fidelity only if a source comparison also ran |
| Run a new visual comparison without UI fixes | Matching source reader → required golden evidence capture → `visual-verification` in comparison-only scope | Fresh source/Flutter/diff artifacts, measurements, inspection and gaps; no UI fixes or regression-baseline promotion |
| Review only | `flutter-review` → mechanical checks and manual inspection | Findings only; no config creation, fixes, installs, captures or baseline updates |

HTML screen/planning sources belong to `html-to-widget`; `set-theme-from-html` applies whole-design foundations after core, sharing the same extraction reference. Figma sources belong to `figma-to-widget`. If a source/tool is unavailable, report the specific missing input and continue work that does not depend on it. Never claim extraction or visual comparison occurred without evidence.

## Responsibility boundaries

- **`flutter-knowledge`:** select scope/route, retain configuration decisions and assemble the final report. It does not repeat specialist recipes.
- **`flutter-init`:** config schema, defaults, discovery and initialization. Its observations do not redefine conventions.
- **Implementation skills:** feature placement, UI/state/data contracts, routing/DI, themes, localization and storage. Invoke only those touched. Accessibility/responsiveness/performance add their scoped responsibilities.
- **Source readers:** inspect source values, geometry, assets, states and interactions; produce source facts for briefs or implementation. Theme decisions belong to `flutter-app-theme`, not a second token policy in the reader.
- **`set-theme-from-html`:** orchestrates whole-HTML foundation application and original asset import after core; shared HTML extraction and `flutter-app-theme` remain the source/value and token API owners. Its component captures establish only the checked foundation scope, never complete app/screen fidelity.
- **`flutter-core`:** shared core creation/completion through owning convention skills, using the readiness gate's full or scoped handoff. Complete only selected responsibilities and their required wiring; return to the calling implementation without recursion or unrelated repairs.
- **`visual-verification`:** coverage, matching source/Flutter profiles, comparison commands, diff inspection, fix loop and evidence report. It calls the shared golden capture reference; fixing stays part of implementation, outside findings-only review.
- **`golden-tests`:** shared capture harness and regression baselines/variants. Capture alone is not design approval. Return capture artifacts to visual verification when it called this skill; do not restart the source-reader workflow.
- **`flutter-review`:** findings-only final gate. It consumes existing evidence and returns gaps; it does not create evidence or certify uninspected images.

## Handoffs and correction loop

Carry the task scope, relevant config selections, source/frame/state identities, affected files, unresolved decisions and verification coverage through each handoff. These can remain in working context; do not create a separate process document for a small task. Multi-screen planning uses the screen briefs as the durable handoff.

Run review after implementing and verifying the requested scope. If implementation was authorized, return actionable review findings to the responsible implementation skill, fix them, then rerun affected checks. Do not make the review helper write changes. A review-only request ends with findings; a capture blocker or missing decision is reported explicitly without relabeling the task as verified.

## One final completion report

Report the implemented/planned scope, files/artifacts, checks actually run and their outcomes, unresolved findings and checks not performed. For design work include each screen/state's status and measured overall/worst-region difference, linking the canonical evidence report owned by `visual-verification`. For planning, link briefs and distinguish proposed from existing foundations; do not fabricate percentages. Review exit 0 means mechanical checks had no blockers, not that manual checks passed. Do not claim full completion while required work remains.

For implemented design scopes also link the calibration, declared state coverage and baseline handoff evidence. Distinguish source fidelity, baseline approval, behavior checks and normal regression; a regression-only approval does not verify the design. Include measured stage work and unavailable usage honestly. A source gap or a failed ordinary golden check cannot disappear into an aggregate success statement.

No workflow authorizes committing, publishing or installing every recommended package as an automatic final step.
