# Set Theme from HTML

`/set-theme-from-html <html-design-path>` prepares app-wide foundations for later `/html-to-widget` screen implementation. Invocation authorizes the scoped theme/asset edits and required checks. It does not authorize scaffolding core, business screens, routes, state/DI replacement, package changes, publishing or a release.

A natural-language request to apply or refresh these app-wide foundations authorizes the same scoped work; no slash command is required. Follow [task routing](../flutter-knowledge/references/workflows.md#natural-language-design-updates) to distinguish an app-wide foundation request from a local screen refresh.

Complete preparation covers all seven theme groups and the original design resources. A scoped refresh such as "update the shared colors and fonts" changes only the requested groups, their necessary component mappings and affected original resources. Inspect their usage across the whole source, preserve unrelated spacing/radii/motion/shapes/assets, and report dependent mismatches instead of silently expanding the update. Its verification and completion claims cover that refresh, not an entirely reapplied theme.

## Source and prerequisites

Read `$ARGUMENTS`, or the invocation text when the harness does not substitute it. A quoted path is one argument. Resolve relative paths from the project cwd, expand leading `~/`, and check readability; treat it as data, never shell code. An HTTP(S) design URL also works. Use a previously supplied source only when unambiguous. A missing, unreadable or ambiguous source is actionable missing input: report the exact supplied identity and request its correction, never substitute a repository HTML file.

Read the [configuration contract](../flutter-init/references/configuration.md), relevant current core/theme files and existing design docs. This runs **after `/flutter-core`**. If the needed core/theme/assets contracts are absent or incomplete, report the needed `/flutter-core` work and continue independent source inspection; do not bootstrap them implicitly. Invoke `flutter-app-theme` before theme edits and the mapped UI/structure skills before changing wrappers/files. The [core contracts](../flutter-core/references/core-contracts.md) identify public APIs to preserve. Retain all seven token groups, selected packages/adapters, MyApp/direct main, global sl, public AppRouter entry decision, root network ownership and observer setup.

## Read the whole design

Read [shared HTML source extraction](../html-to-widget/references/source-extraction.md), the sole owner of computed CSS/fonts/motion/state extraction. Inspect the entire provided design, all reachable screens/views, shared components and supplied light/dark themes, rather than deriving common defaults from its first screen. Inventory routes/state triggers and unreachable or broken portions. Drive selected, disabled, focus, hover, loading/error, sheet/dialog and component variants where supplied. Capture profiles identify screen/root, theme, state, viewport, DPR, locale, data, focus/pointer and animation frame.

Use the actual browser, shared `layoutTree`/`captureComposition`, CSSOM and loaded fonts. The companion [foundation snapshot](references/helpers.md#browser-snapshot) retains app-wide facts and resource references for each observed profile; it does not navigate, infer roles, cover hidden states or prove fidelity. Inspect stylesheets, scripts and declared resources as well as current rendering. Screenshots or regex-only CSS guesses cannot establish these foundations. Unavailable CSSOM, unresolved resources and unvisited states remain gaps.

## Import original assets and apply foundations

Read [asset import and application](references/assets-and-application.md) and [foundation application proof](references/foundation-proof.md). Import actual source bytes/vectors into existing asset directories, preserving font families/weights/styles, SVG dependencies, licenses and provenance. Do not replace assets with emoji, Material icons, AI images or a different font. The [explicit-manifest importer](references/helpers.md#asset-import) resolves source/CSS bases, validates resources and safely deduplicates files; its report is import evidence, not theme or visual approval. Edit AppAssets and pubspec intentionally from that report, preserving typed prefixes and the translations getter. Run the read-only font-plan audit against actual registrations, AppFonts/consumer bindings, CSS declarations and selected visible-string/locale coverage; importer success cannot approve an effective face. Do not add unrelated dependencies.

`flutter-app-theme` owns API, slot/token naming and Material/component mappings. This command makes measured design values authoritative under its source-of-truth rule: add semantic tokens where needed; never silently round to a nearest step. Map source roles to AppSkin, space, radius, text/fonts, elevation, motion and shape, then AppTheme/ColorScheme and actual wrappers. Account for every observed role before handoff, including rich typography, constrained widths, quiet/task/divider styles, shared-control variants and paint/composition. Compare common defaults across every supplied theme/variant. Tokens require actual core consumers; theme owns component default/variant APIs while html-to-widget owns feature placement. Resolve conflicting roles through appropriate component slots/variants; do not choose the first screen's value arbitrarily. Preserve existing unrelated roles and modes. Unprovided roles/modes remain explicitly unchanged, derived or provisional, never source-matched; do not invent a dark/brand palette. Unsupported CSS or installed API limitations remain actionable fidelity gaps. Honor project no-comments instructions over optional token documentation conventions; put explanations in the mapping report when needed.

## Verify and hand off

Write a mapping report under the project's existing `docs/design/`: the source inventory and profiles, observed CSS facts kept separate from implementation choices, and one row per source role or resource naming its token, asset or wrapper consumer. Mark each row `extracted`, `applied` or `visually checked`, and list provisional, unchanged and unsupported roles with reasons. Link source extraction evidence rather than copying the recipe. Avoid shipped absolute source-machine paths or credentials.

Invoke `visual-verification` and its [shared golden capture](../golden-tests/references/capture.md) for a compact set of source-backed component checks in every supplied skin: each shared control variant, text role and paint role the screens will reuse. Render the **actual applied project theme, skins, loaded fonts and core wrappers**; a separately styled replica proves nothing. This command does not implement screens or need a full-screen matrix. No threshold loosening, resized comparisons or ignored gaps. A composite's PASS cannot approve a failing child. Motion and shape behavior static PNGs cannot show need their own evidence.

Use the additive [component calibration preflight](../visual-verification/references/preflight.md#reusable-component-calibration) to check effective runtime typography, viewport/crop scaling, painted field bounds and glow overlap before these component comparisons. Reuse it only with matching inspected fingerprints; it never approves later screens.

Run `flutter-review` as the final findings-only gate. State only the checked roles and components as verified, never an entire app. Report files, executed checks and remaining gaps, then hand the mapping report, imported assets and source profiles to `html-to-widget`, which builds screens on these foundations and still runs its own source comparison. Fixes made later during screen work belong to that stage and are reported there. When the user asks for an auditable proof, add the [optional strict handoff gate](references/strict-handoff-gate.md).

For later reuse follow the [validated source cache](../visual-verification/references/design-cache.md). Include CSS, scripts, fonts, icons/images and runtime dependencies plus the companion extractor in freshness inputs; unchanged HTML alone is insufficient. A cache hit reuses source facts only, never verifies current Flutter output.
