One catalog, three kinds of knowledge

Package independence means separating policy from mechanism. It does not mean every existing instruction is portable unchanged.

Conventions / approaches

Agreed structure, boundaries, ownership and verification practices. Kept fixed while package mechanics adapt.

Package implementations

Library-specific types, APIs, lifecycle and generators. Selected through supported adapters.

Project contracts

Your own token, API, result and widget interfaces. Discovered from source or explicitly bound in configuration.

What YAML would do

Select the project’s implementation choices and bind its existing contracts, so only the relevant implementation guidance loads.

What YAML cannot do alone

Create a correct adapter by naming a package, or make incompatible state / routing / lifecycle rules equivalent. Those mappings must be designed and tested.

Configuration resolution behavior

01
Read explicit choices and inspect the project

Check pubspec.yaml, the lockfile, project instructions and real APIs. Do not assume configuration can override the actual installed versions or user constraints.

02
Resolve omissions, mismatches and unsupported combinations

Infer an unambiguous existing choice when configuration is absent. Surface a declared-but-missing package, multiple plausible stacks or a missing adapter before dependent code is written. Do not auto-install or migrate just because YAML names a choice.

03
Load the shared policy and only relevant adapters

State, routing, DI, UI, localization and tests must use compatible ownership and lifecycle rules. A single package change can affect several skills.

04
Verify the implementation and record unresolved decisions

Use adapter-appropriate analysis / tests and rule checks. Do not claim a package combination is supported until its guidance has been validated.

Source-of-truth design

Keep conventions written once, with package-specific details in scoped adapter references. The YAML chooses them; it should not become another copy of the guidance. Custom paths identify entry points, but the agent must still inspect their actual interfaces.

Decisions before implementation

Your conventions stay fixed. These review questions explain the boundaries retained by the implementation and the validation still needed for additional package combinations.

01 / CONVENTION SCOPE

What must stay consistent?

Folder tree, Screen / Body split, naming and dependency direction can be intentional conventions. Nullable models, fixed base URLs and controller ownership deserve individual decisions.

Suggested direction: explicitly approve a shared preset; avoid calling every current rule universal.

02 / STATE CONTRACT

How portable is the state model?

Constructor fetching, payload-free success states and mutable data on a Cubit are connected choices. They will shape every state adapter and its UI / tests.

Suggested direction: define ownership and observable behavior first; allow adapter-native representation where needed.

03 / PACKAGE COVERAGE

Which combinations are supported?

Allowing any package string creates a promise the guidance cannot necessarily fulfill. Cross-package combinations need compatibility checks.

Suggested direction: begin with the documented current stack; add one alternate stack only after its adapter passes checks.

04 / CUSTOM CONTRACTS

How much should the project supply?

ApiConsumer, Result, AppTokens and wrappers are not package selections. A name / path alone is insufficient if signatures or behavior differ.

Suggested direction: inspect existing contracts, with explicit bindings for ambiguous or nonstandard projects.

05 / ADAPTER OWNERSHIP

Skills or references?

Cubit and the two storage engines are candidates for shared intent with selected implementation references. Existing skill names can remain compatibility entry points during migration.

Suggested direction: keep task-facing skills small; load adapters progressively; avoid a new skill for every possible combination.

06 / VISUAL CAPTURE

Which layer owns the harness?

Design comparison and regression tests both need a deterministic Flutter capture, while the wrapper depends on state, theme and localization.

Suggested direction: share capture mechanics; keep comparison and baseline approval as separate workflows.

07 / CONFIGURATION CONFLICTS

What happens when YAML disagrees?

A configured package may be absent, too old for its adapter or mixed with another stack. Existing project rules can also conflict with the preset.

Suggested direction: explain the conflict and stop dependent changes; migrations need explicit scope.

08 / TEST & DESIGN POLICY

What should never be implicit?

Resolve unit-test permission, DI test updates and automatic goldens once. Also decide whether exact design values or the token scale take priority.

Suggested direction: keep these as shared workflow policies, separate from package selectors.
