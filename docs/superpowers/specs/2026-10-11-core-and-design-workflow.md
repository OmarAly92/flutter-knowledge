# Core setup and design workflow

User-approved scope: implement all five improvements discussed after the reviewed three-screen run, and add a manually invoked `/flutter-core` skill using the reference app's core approaches. No authored code comments. The reference-app checkout and reviewed fixture remain reference material; the new evaluation starts from a minimal Flutter project. No commit, merge or release is authorized.

`flutter-core` initializes package choices through `flutter-init` if config is absent, then inspects the actual project contracts. It creates missing essentials and completes incomplete ones while preserving custom routes, feature registrations, theme values, assets, locales and startup effects. It is not an ordinary screen-work side effect. Existing alternative packages keep the architectural naming, owner lifetimes, Screen/Body and token conventions. Existing older theme architecture is not migrated implicitly.

Essentials: router/routes/navigation extensions; core DI and app registration; all seven token groups, skins, JSON registry/loading and skin selection; API consumer with configured transport, options/interceptors, endpoints and GlobalResponse; Result/Failure/error mapping; network status; layout/inset helpers; localization and generated accessors; preferences/logger; text, scaffold/appbar, container, spaces, buttons, fields, sheets and feedback wrappers; application-root wiring.

Reference-app-specific auth/session policy, backend URL, chat storage, socket/voice/personalization, branding and screen-specific tokens are excluded. Transport retains normal certificate validation and does not log tokens. Missing backend configuration remains explicit. Package recommendations do not cause unrelated database/code-generation/toolkit installation.

Design work begins with shared-core/capture preflight and complete visible composition extraction. Captures assert expected state; dimensions, DPR, insets, theme, locale, scale, fonts, shadows, motion and pointer state are controlled. The HTML helper records the capture boundary and visible content outside the requested screen subtree. Early checks exercise relevant pending operations and Arabic/large-text/narrow/keyboard interactions before visual polish.

A reusable runner invokes the existing Flutter golden camera and comparator, preserves unique attempts and full failures, produces structured evidence, and never turns a numeric pass into visual verification. A separate hash-bound inspection record can finalize inspected rows. Source/reference reuse remains governed by the existing cache contract and never reuses Flutter verification. Default scoring and comparison exits remain unchanged.

Acceptance: focused script/unit tests; fresh core generated via the skill without reference-app code supplied; absent-init and partial-core behavior; core API/theme/DI/localization/widget preflight; original three-screen HTML flow built on that core with preserved conventions; all source-backed rows and relevant regression variants inspected; final analysis/tests and an honest comparison with the prior reviewed run. Before merging SKILL changes, the repository benchmark must be rerun; no merge occurs in this task.
